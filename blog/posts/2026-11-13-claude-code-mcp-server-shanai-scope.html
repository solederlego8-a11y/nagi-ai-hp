Claude Code のMCPサーバー接続を社内で決める方法｜3つのスコープと承認のルール

更新日：2026年11月13日｜執筆：凪AI（運営：フォローズ）編集部

Claude Codeを社内に広げると、次に出てくるのが「外部ツールとつないでよいのか」という質問です。課題管理や監視ダッシュボードの情報を毎回チャットに貼り付ける代わりに、MCP（Model Context Protocol）のサーバーを接続すると、Claude Codeからその仕組みを直接読み書きできます。便利な反面、接続先ごとに「誰が・どのプロジェクトで・何に触れるか」が増えるため、個人の判断で増やし続けると実態が見えなくなります。この記事では、Anthropic公式ドキュメント「Connect Claude Code to tools via MCP」（確認日：2026-11-13）の記載だけを使い、接続の置き場所を決める3つのスコープ、projectスコープの承認、管理側でできる配布と制限を整理します。実行そのものの可否は権限設定（permissions）の決め方の記事で扱っているため、本記事は「接続先をどう管理するか」に絞ります。

30秒で判断
  • MCPサーバーの置き場所は3つのスコープ。local（既定・そのプロジェクトだけ・非共有）、project（.mcp.json でチーム共有）、user（自分の全プロジェクト・非共有）
  • projectスコープは使う前に承認の確認があり、クローンしたリポジトリ自身は承認できない。認証情報を含むサーバーは、バージョン管理に入らない local が公式の案内
  • 同名のサーバーは local → project → user の順に優先され、定義は丸ごと1つだけが使われる。管理側は管理用設定で配布と制限ができる

関連：実行の可否は権限設定の決め方、入力情報のルールは情報漏えい対策の社内ルール

MCPサーバーを接続すると、何ができるようになりますか？

公式ドキュメント（確認日：2026-11-13）によると、MCPはAIと外部ツールを連携させるためのオープンな標準で、接続したサーバーを通じて、Claude Codeが課題管理・データベース・APIなどの外部の仕組みにアクセスできます。公式の例としては、課題トラッカーの内容から機能を実装する、監視データを確認する、データベースに問い合わせる、といった使い方が挙げられています。

接続の方式（トランスポート）は、リモートのHTTP（推奨）、SSE、自分のマシンでプロセスとして動く stdio、WebSocket の4種類が案内されています。追加は claude mcp add コマンドで行い、リモートは --transport http とURL、stdio は起動コマンドを指定します。方式の違いよりも社内管理で重要なのは、次の「どこに設定を置くか」です。接続先が社内システムに触れる以上、設定の置き場所が、そのまま共有範囲と責任の範囲になります。

出典：Anthropic「Connect Claude Code to tools via MCP」（code.claude.com/docs/en/mcp）、確認日 2026-11-13。

3つのスコープ ― 置き場所が共有範囲を決める

公式ドキュメントでは、MCPサーバーの設定スコープは次の3つです。

スコープ読み込まれる範囲チーム共有保存先向いている用途（公式の案内）
local（既定）追加したプロジェクトだけされない~/.claude.json（そのプロジェクトの配下）個人の開発用サーバー、試行中の設定、バージョン管理に入れたくない認証情報を使うサーバー
projectそのプロジェクトされるプロジェクト直下の .mcp.jsonチーム全員で同じ接続先を使う場合。.mcp.json をバージョン管理に登録して共有する
user自分の全プロジェクトされない~/.claude.jsonプロジェクトをまたいで頻繁に使う、個人用のユーティリティや開発ツール

社内ルールへの落とし込みはシンプルです。チームで使うと決めたものだけを project に置き、試行中・個人用・認証情報を伴うものは local に置く。user は「個人の道具箱」として、業務システムへの接続には使わない、と決めておくと、棚卸しのときに迷いません。

projectスコープには承認の仕組みがあります

.mcp.json はリポジトリに入るファイルなので、受け取る側の安全のために承認の仕組みが用意されています。公式ドキュメントの要点は次のとおりです。

  • projectスコープのサーバーは、対話セッションで使う前に、承認の確認が表示される
  • クローンしたリポジトリ自身が、そのリポジトリのサーバーを承認することはできない。リポジトリに登録された設定による自動承認は、未信頼のフォルダでは無視される
  • 承認の選択は claude mcp reset-project-choices でリセットできる
  • 接続状態は claude mcp list や /mcp で確認でき、「承認待ち（Pending approval）」「企業ポリシーでブロック」といった状態も表示される

つまり、.mcp.json をマージする行為は「接続先の候補を配る」までで、実際に使うかどうかは各利用者の承認が別に要ります。コードレビューでは .mcp.json の差分もレビュー対象に含める、という運用を合わせて決めておくと、候補の入口と承認の出口の両方が管理できます。

同名のサーバーと、認証情報の置き場所

同じ名前のサーバーが複数のスコープで定義されている場合、優先順位は local → project → user で、最も優先される定義だけが丸ごと使われ、項目ごとに混ざることはありません。便利な上書きの仕組みですが、裏返すと「チームの定義を使っているつもりで、個人の local 定義につながっていた」という事故が起き得ます。棚卸しでは、サーバーの一覧だけでなく、同名の重複がないかも確認項目に入れてください。

認証情報については、公式ドキュメントが用途の目安として、バージョン管理に入れたくない認証情報を使うサーバーは local スコープを使うことを案内しています。.mcp.json は共有が前提のファイルなので、キーやトークンの実値を書く場所ではありません。共有したい場合は、認証は各利用者が自分の側で行う形にし、ファイルには接続先の定義だけを置くのが原則です。

管理者は、配布と制限ができますか？

できます。公式ドキュメントでは、管理者が管理用のMCP設定で、組織の全利用者向けにサーバーを配布できること、そしてポリシーでサーバーを制限できることが説明されています。ポリシーでブロックされたサーバーは、接続状態の確認でその旨が表示されます（ポリシーの種類によっては一覧自体に表示されません）。

権限設定の記事で整理した「固定する層」と「現場に任せる層」の考え方は、MCPでも同じです。

  • 管理側で決める層：接続してよい業務システムの範囲、管理用設定で配る標準のサーバー、禁止する接続先
  • プロジェクトで決める層：.mcp.json に置くチーム共有のサーバーと、そのレビュー方法
  • 個人に任せる層：local・user スコープの個人用サーバー。ただし業務システムへの接続は含めない

よくある質問

Q. projectスコープで共有すれば、チーム全員がそのまま使えますか

いいえ。projectスコープのサーバーは、対話セッションで使う前に承認の確認が表示されます。クローンしたリポジトリ自身がそのサーバーを承認することはできず、承認は利用者側や管理設定など、リポジトリ外の設定から行われます。公式ドキュメント（確認日：2026-11-13）の記載です。

Q. APIキーなどの認証情報を、.mcp.json に書いて共有してよいですか

推奨しません。.mcp.json はバージョン管理に登録して共有するファイルです。公式ドキュメントでも、バージョン管理に入れたくない認証情報を使うサーバーは、個人の local スコープで追加することが案内されています。

Q. 同じ名前のサーバーを複数のスコープで定義したら、どうなりますか

local、project、user の順に優先され、最も優先されるスコープの定義だけが丸ごと使われます。項目ごとに混ざることはありません。同名の定義が残っていると、意図しない接続先につながるため、棚卸しでは同名の重複も確認します。

Q. 管理者は、利用者が接続できるMCPサーバーを制限できますか

管理用のMCP設定で、組織の全利用者向けにサーバーを配布したり、ポリシーでサーバーを制限したりできます。ポリシーでブロックされたサーバーは、接続状態の確認画面でその旨が表示されます。詳細は公式ドキュメントの managed MCP configuration の説明を確認してください。

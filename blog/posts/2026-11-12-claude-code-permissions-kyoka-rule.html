Claude Code の権限設定（permissions）の決め方｜許可・確認・拒否とモードの社内ルール

更新日：2026年11月12日｜執筆：凪AI（運営：フォローズ）編集部

Claude Codeを社員に配るとき、情シスや管理者から必ず出るのが「どこまで勝手に実行させてよいのか」という質問です。ファイルの書き換えやコマンドの実行を毎回止めていては生産性が上がらず、逆にすべて自動で通せば事故のもとになります。この記事では、Anthropic公式ドキュメント「Configure permissions」（確認日：2026-11-12）の記載だけを使い、権限ルールの3種類と評価順序、6つの権限モード、管理設定で固定できる範囲を整理します。入力してよい情報の線引きは情報漏えい対策の社内ルールの記事で扱っているため、本記事は「実行の可否をどう制御するか」に絞ります。

30秒で判断
  • 権限ルールは許可（allow）・確認（ask）・拒否（deny）の3種類。評価は deny → ask → allow の順で、最初に一致したものが決める。広い deny は狭い allow では例外化できない
  • 権限モードは6種類（default、acceptEdits、plan、auto、dontAsk、bypassPermissions）。既定は設定ファイルの defaultMode で決められる
  • bypassPermissions と auto は、管理設定で利用者側から有効化できないよう固定できる。社内ルールは「モードの既定」と「deny の初期セット」を先に決めるのが要点

Claude Codeの権限は、そもそも何を決める仕組みですか？

公式ドキュメント（確認日：2026-11-12）によると、Claude Codeはツール（読み取り、コマンド実行、ファイル変更など）の種類ごとに、実行前に利用者の承認が要るかどうかを分ける段階的な権限の仕組みを持っています。権限設定はバージョン管理に登録して組織内の開発者全員で共有でき、各開発者が自分の分をカスタマイズすることもできます。既定のモード（Manual）で、ツールの種類ごとに承認がどうなるかは次のとおりです。

ツールの種類例既定で承認が要るか「今後確認しない」を選んだ場合
読み取り専用ファイルの読み取り、検索作業ディレクトリと追加ディレクトリの範囲内では不要対象外
Bashコマンドシェルの実行必要（読み取り専用の組み込みコマンド群を除く）リポジトリとコマンドの単位で恒久的に保存される
ファイルの変更ファイルの編集・作成必要セッションが終わるまで有効
WebフェッチWebFetch必要（事前承認済みのドキュメントのドメインを除く）リポジトリとドメインの単位で恒久的に保存される
Web検索WebSearch必要リポジトリの単位で恒久的に保存される

出典：Anthropic「Configure permissions」（code.claude.com/docs/en/permissions）、確認日 2026-11-12。恒久的に保存される承認は、リポジトリ直下の .claude/settings.local.json にルールとして書き込まれ、同じリポジトリの今後のセッションに効きます。つまり、「現場が日々の承認で育てたルール」と「情シスが配るルール」が、同じ設定の仕組みの上で積み重なっていく構造です。

許可・確認・拒否の3種類のルールと、評価の順序

権限ルールは、/permissions コマンドの画面で一覧でき、どの設定ファイルに由来するルールかもあわせて表示されます。ルールは次の3種類です。

  • allow（許可）：指定したツールを、手動の承認なしに使えるようにする
  • ask（確認）：指定したツールを使おうとするたびに、確認のプロンプトを出す
  • deny（拒否）：指定したツールの使用そのものを防ぐ

ルールの書き方は Tool または Tool(specifier) の形式で、公式ドキュメントには次のような例が挙げられています。

  • Bash(npm run build)：コマンド npm run build そのものに一致
  • Read(./.env)：カレントディレクトリの .env ファイルの読み取りに一致
  • WebFetch(domain:example.com)：example.com へのフェッチに一致

管理上いちばん重要なのは評価の順序です。公式ドキュメントでは、ルールは deny → ask → allow の順に評価され、最初に一致したものが結果を決める、と説明されています。たとえば広い deny ルール Bash(aws *) は、それより狭い allow ルール Bash(aws s3 ls) に一致する呼び出しも含めてすべてを止めます。allow で deny の例外を切り出すことはできません。「禁止を土台にして、許可で穴を開ける」という設計はできないため、社内ルールでは、まず deny で止める範囲を決め、その内側で allow と ask を配る順序で考える必要があります。なお、Bash のようにツール名だけの deny ルールは、そのツールをClaudeの文脈から取り除き、そもそも見えなくします。

権限モードは6種類。既定をどれにするか

個別のルールとは別に、承認の進め方全体を切り替える「権限モード」があります。公式ドキュメント（確認日：2026-11-12）に挙げられているのは次の6種類です。新しいセッションの既定のモードは、設定ファイルの defaultMode で決められます。

モード動き
default（Manual）各ツールを初めて使うときに権限を確認する。CLIや各種エディタ拡張では「Manual」と表示される
acceptEditsファイルの編集と、作業ディレクトリ内の一般的なファイル操作コマンド（mkdir、touch、mv、cp など）を自動で承認する
planファイルの読み取りと読み取り専用コマンドで調査だけを行い、ソースファイルは編集しない
auto通常の確認は出さず、シェルコマンドやネットワーク要求の前に、背景の分類器が要求に沿った操作かどうかを検査する
dontAsk通常なら確認が出る呼び出しを自動で拒否する。事前に許可されたツールや、確認不要の操作はそのまま動く
bypassPermissions権限の確認を省略する（一部の操作はどのモードでも自動承認されない）

現場の体感としては、default は安全だが承認の回数が多く、acceptEdits は編集作業の速度が上がる一方でコマンド実行の確認は残る、という位置づけです。どのモードを既定にするかは、扱うコードベースの性質（本番に近いデータや認証情報を含むか）で決めるのが現実的です。研修や検証のように「まず触らせる」場面では plan や default、定型の編集作業が中心の部門では acceptEdits、という使い分けが考えられます。社内展開の順番そのものは社内展開の手順の記事で整理しています。

管理者は、利用者側で変えられない形で固定できますか？

できます。公式ドキュメント（確認日：2026-11-12）では、permissions.disableBypassPermissionsMode または permissions.disableAutoMode を "disable" に設定すると、bypassPermissions モードや auto モードを使えなくできる、と説明されています。そして、こうした設定は、上書きできない管理設定（managed settings）に置いたときに最も有効である、と明記されています。

つまり統制の設計は、次の2層で考えます。

  • 管理設定で固定する層：bypassPermissions・auto の可否など、利用者に委ねない項目
  • 共有設定と現場に任せる層：プロジェクト共有の allow リスト、日々の承認で settings.local.json に貯まるルール

すべてを管理設定で固めると、現場の承認ルールが育たず、かえって申請と例外対応が増えます。逆に固定する層が空だと、モードの選択が利用者任せになり、部門ごとに実態がばらけます。「禁止モードの固定」と「deny の初期セット」だけを管理側で持ち、残りは共有設定として配って育てる、という配分が公式の仕組みに沿った形です。

よくある質問

Q. 許可・確認・拒否のルールは、どれが優先されますか

deny、ask、allow の順に評価され、最初に一致したルールが結果を決めます。広い deny ルールに一致する操作は、それより狭い allow ルールでは例外化できません。公式ドキュメント（確認日：2026-11-12）の記載です。

Q. 「今後確認しない」を選ぶと、どこまで効きますか

ツールの種類で異なります。Bashコマンドはリポジトリとコマンドの単位で恒久的に保存され、Webフェッチはドメインの単位で恒久的に保存されます。ファイル変更の承認はセッションが終わるまでです。恒久ルールは .claude/settings.local.json に保存されます。

Q. bypassPermissionsモードを社内で禁止できますか

できます。管理設定で permissions.disableBypassPermissionsMode を "disable" に設定します。autoモードも permissions.disableAutoMode で同様に無効化できます。

Q. 現在効いているルールは、どこで確認できますか

/permissions コマンドの画面で、すべての権限ルールと、それぞれのルールが由来する設定ファイルを一覧できます。ルールの追加・削除は、その場で次のツール呼び出しから反映されます。
